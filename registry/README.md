# Реестр пакетов Swift на Cloudflare Workers

Реализация [SE-0292](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0292-package-registry-service.md) — того самого пакетного реестра, который в [основном документе](https://github.com/yklishevich/kufar-ios-demo/blob/main/architecture-ios-app.md) назван промышленной альтернативой гит-зависимостям.

**Демо переведено на него целиком:** все 87 зависимостей в двадцати манифестах объявлены через `.package(id:)`, гит-URL не осталось ни одного. Реестр обслуживает настоящие пакеты `kufar.*` из репозиториев команд, а не отдельную песочницу.

## Зачем реестр вообще

Одна фраза объясняет всё остальное:

> В гит-зависимостях **identity пакета — это его адрес**. В реестре **identity — это имя**.

Из адреса следует цепочка: URL указывает на репозиторий → манифест ищется в корне → версия это тег → тег принадлежит репозиторию целиком → **один пакет на репозиторий**. Реестр разрывает её в первом же звене: `kufar.Toolbox` — имя, а где лежат исходники, знает только реестр. Отсюда и несколько пакетов из одного репозитория, и переезд между репозиториями, невидимый для потребителей.

## Устройство

```
Worker ── D1  метаданные релизов: версии, checksum, манифесты
   └───── R2  архивы исходников
```

Разделение не косметическое. Список релизов — это запрос с сортировкой по semver, листинг бакета так не умеет и `checksum` не хранит. Архивы — блобы по несколько мегабайт, в D1 им нечего делать. Манифест лежит в D1, хотя это файл: он маленький и запрашивается при каждом резолве, лишний поход в объектное хранилище дороже строки в базе.

## Что реализовано

| Эндпоинт | Назначение |
|---|---|
| `GET /{scope}/{name}` | список релизов, `Link: rel="latest-version"` |
| `GET /{scope}/{name}/{version}` | метаданные, контрольная сумма архива |
| `GET /{scope}/{name}/{version}/Package.swift` | манифест, `?swift-version=` для версионных |
| `GET /{scope}/{name}/{version}.zip` | архив, `Digest: sha-256=…` |
| `GET /identifiers?url=…` | обратный поиск идентификатора по гит-URL |
| `PUT /_publish` | публикация — **не** из спецификации, см. ниже |

Плюс то, что легко забыть и что ломается молча: согласование версии API через `Accept: application/vnd.swift.registry.v1+json`, заголовок `Content-Version` в каждом ответе, ошибки в `application/problem+json`.

Версия API живёт в `Accept`, а не в пути — решение спецификации, и оно правильное: адрес релиза остаётся стабильным навсегда, а о формате клиент договаривается отдельно.

## Чего нет и почему

**SE-0391 — публикация по стандарту.** `PUT /{scope}/{name}/{version}` с multipart-телом, `swift package-registry publish`, подписи CMS и политика «принимать только подписанное». Вместо него узкий собственный `PUT /_publish` с bearer-токеном: архив собирает CI, он же считает сумму, серверу остаётся положить блоб и вставить строку.

Размен назван честно: стандартная CLI-публикация с этим реестром не работает, публиковать может только свой пайплайн. Взамен нет ни разбора multipart, ни валидации подписей — то есть нет и половины поверхности для ошибок. А демонстрируется всё равно чтение: именно его использует SwiftPM при резолве. Добавить SE-0391 — это ещё один маршрут, схема хранения не меняется.

**Аутентификация чтения.** Реестр публичный на чтение. Приватному нужны токены в `registries.json` и проверка на каждом GET — механически просто, к архитектуре ничего не добавляет.

**Зеркалирование и вытеснение кеша.** Реальный реестр держит кеш популярных версий ближе к клиентам. R2 и так раздаётся с края сети Cloudflare, поэтому здесь это было бы решением несуществующей задачи.

## Запуск локально

```bash
npm install
npm run db:init          # схема в локальный D1
npm run dev              # wrangler dev на :8787
npm test                 # тесты контракта эндпоинтов
```

Тесты идут в настоящем `workerd` через miniflare, а не в ноде с моками: R2 и D1 подменяются локальными реализациями, но поведение `Request`, `Headers` и `crypto.subtle` остаётся тем же, что в проде. Мок на `fetch` проверял бы наши представления о рантайме, а не рантайм.

## Деплой

Реестр живёт на **`https://spm-registry.byklishevich.com`**.

```bash
wrangler r2 bucket create spm-registry-archives
wrangler d1 create spm-registry              # id вписать в wrangler.toml
npm run db:init:remote
wrangler secret put PUBLISH_TOKEN
npm run deploy                                 # заведёт DNS и сертификат сам
```

Свой домен, а не `*.workers.dev`, — и это не про красоту. Адрес реестра попадает в `registries.json` каждого потребителя и в `Package.resolved` каждой сборки. Переехать с него потом нельзя без одновременной правки у всех — ровно та жёсткость, от которой реестр и должен избавлять. Поддомен на своём домене переносится между провайдерами, `*.workers.dev` — нет.

`REGISTRY_BASE_URL` задан явно, а не выводится из запроса: Worker стоит за прокси, и `Host` не обязан совпадать с адресом, по которому клиент пойдёт дальше по выданным ссылкам.

## Публикация

По тегу вида `kufar.Foundation-1.2.3` — идентичность пакета плюс версия. Идентичность совпадает с именем папки, поэтому адресат читается из тега без вычисления diff по путям.

Теги ставятся **в репозиториях команд**, а не в воркспейсе. Повседневный путь — `./Tools/publish.sh --push --tag` из рабочей копии; workflow [`registry-publish.yml`](https://github.com/yklishevich/kufar-ios-demo/blob/main/.github/workflows/registry-publish.yml) делает то же самое по `workflow_dispatch` и служит эталоном.

Триггер именно тег, а не push в ветку. Публикация на каждый коммит превратила бы версию из решения в побочный эффект, и `from: "1.0.0"` у потребителей начал бы подтягивать чужие промежуточные состояния — то есть HEAD-режим, только медленнее и с иллюзией версионирования.

Вручную:

```bash
REGISTRY_URL=https://spm-registry.byklishevich.com PUBLISH_TOKEN=… \
  node scripts/publish.mjs --package ../platform_team/kufar.Foundation \
                           --scope kufar --name Foundation --version 1.0.0
```

Архив собирает клиент через `swift package archive-source`, а не сервер: тулчейн знает, что относится к пакету, а что нет — уважает `.gitignore`, выкидывает `.build`. Повторять эту логику на сервере значит однажды разойтись с тулчейном и опубликовать архив, который не собирается.

Контрольную сумму сверяет **R2 при записи**, а не Worker. Смысл проверки прежний — то, что легло в хранилище, обязано совпасть с подписью пайплайна, иначе ошибка публикации превратится в ошибку резолва у всех потребителей и всплывёт через месяц. Но считать sha256 по многомегабайтному архиву в самом Worker'е дорого: на бесплатном тарифе бюджет 10 мс CPU на вызов, и публикация — единственное место, которое в него не укладывалось. R2 проверяет сумму на своей стороне и отвергает объект при расхождении: гарантия та же, CPU ноль.

## Проверить резолв вживую

Публиковать нужно в порядке зависимости — потребитель не соберётся, пока в реестре нет того, на что он ссылается. Самая короткая цепочка в демо:

```bash
export REGISTRY_URL=https://spm-registry.byklishevich.com PUBLISH_TOKEN=…
cd registry
node scripts/publish.mjs --package ../platform_team/kufar.Foundation \
                        --scope kufar --name Foundation --version 1.0.0
node scripts/publish.mjs --package ../goods_team/kufar.GoodsContracts \
                        --scope kufar --name GoodsContracts --version 1.0.0
```

`kufar.GoodsContracts` просит только `kufar.Foundation`, и тот приезжает транзитивно — то есть проверяется **резолв цепочки**, а не скачивание одного архива.

Главное свойство здесь видно на `search_team`: `kufar.CatalogContracts`, `kufar.SearchContracts` и `kufar.Search` лежат в одном репозитории и релизятся независимо. С гит-URL так нельзя — манифест ищется в корне, а тег принадлежит репозиторию целиком. Ради этого всё и затевалось.

Настройка реестра лежит в `.swiftpm/configuration/registries.json` **каждого пакета**, а не в домашнем каталоге: клонировал и собрал, настраивать нечего.

## Работает ли локальная подмена — проверка перед миграцией

От ответа зависит, можно ли переводить `kufar-ios` на реестр.

Разработка там держится на локальной подмене: правишь `SharedKernel` — правка сразу видна в `GoodsUI`, без тега. Механизм сопоставляет зависимость с папкой **по identity**. Для гит-URL identity — последний компонент адреса, `KufarFoundation`, совпадает с именем папки. Для реестра identity — `kufar.KufarFoundation`, со скоупом. Совпадёт ли одно с другим, в документации не сказано.

```bash
./scripts/substitution-check.sh
```

### Первый ответ — и почему он оказался неверным

```
error: 'kufar.Toolbox': registry dependency 'kufar.Toolbox' can't be edited
```

Отказ по **классу зависимости**, а не по имени или версии. Объяснение напрашивалось само: пакет из реестра приезжает архивом с контрольной суммой, локальная папка эту сумму ломает, значит реестр не может одновременно гарантировать целостность и позволять подставлять что угодно. Отсюда следовал вывод «подмена с реестром невозможна, демо остаётся на гит-зависимостях», и он был записан сюда как окончательный.

Вывод неверный. Проверялся `swift package edit` — механизм, который вынимает зависимость в редактируемую копию и помечает её в `Package.resolved`. Подмена в воркспейсе Xcode — **не он**. Там нет ни пометки, ни копии: Xcode просто видит в том же `.xcworkspace` локальный пакет и берёт его вместо разрешённой зависимости. Один отказ был распространён на второй механизм по сходству названия.

### Второй эксперимент: тот же вопрос, но в Xcode

Пакеты положены в воркспейс рядом — и Xcode ответил не отказом, а требованием:

```
error: unable to override package 'Foundation' because its identity
'kufar.foundation' doesn't match override's identity
(directory name) 'foundation'
```

Это не «нельзя». Это «можно, но имя папки обязано совпадать с идентичностью». Правило нигде не документировано, а следствие из него прямое:

```
папка kufar.Foundation  →  подмена работает
папка KufarFoundation   →  молча выключается
```

Молча — потому что при несовпадении Xcode не подменяет, а честно тянет версию из реестра. Сборка идёт, правки не видны, и причина не выводится ни из чего.

### Что из этого следует для kufar-ios

Ограничения, ради которого затевалась проверка, не существует. Значит платить за реестр ежедневным трением не нужно, и обходные пути — локальный `wrangler dev`, предрелизы на каждую правку — не понадобились.

Поэтому демо переведено на реестр целиком: 21 репозиторий-на-пакет свёрнут в 6 репозиториев по командам, папки переименованы в `kufar.Name`, манифесты — на `.package(id:)`. Пакеты одной команды лежат вместе и релизятся независимо (теги вида `kufar.Foundation-1.2.0`), а локальная разработка осталась прежней: правка в `SharedKernel` видна в `GoodsUI` сразу.

Ценность папки `registry/` — в этой паре экспериментов, а не в первом. Первый дал правдоподобный ответ, согласующийся с документацией и с здравым смыслом про контрольные суммы; неверным он был не в наблюдении, а в переносе наблюдения на соседний механизм. Разница между «CLI отказал» и «нельзя» стоила бы здесь всей архитектуры многорепозиторного демо.

### Побочная находка: подписи

```
error: kufar.DesignComponents version 1.2.0 source archive
       from https://spm-registry.byklishevich.com is not signed
```

SE-0391 добавил в реестры подпись архивов, и SwiftPM спрашивает у клиента, что делать с неподписанным: ключ `signing.onUnsigned` в `registries.json`. Значение по умолчанию — `prompt`, вопрос человеку. В CLI это работает, а резолв в Xcode неинтерактивен, и `prompt` там вырождается в отказ. Наш реестр не подписывает (SE-0391 не реализован намеренно), поэтому политика задана явно и закоммичена:

```json
"security": {
  "registryOverrides": {
    "spm-registry.byklishevich.com": {
      "signing": { "onUnsigned": "silentAllow" }
    }
  }
}
```

`registryOverrides`, а не `default`: послабление адресное, для одного своего хоста. Настройка в `default` сняла бы проверку подписи со **всех** реестров, включая те, что появятся позже, — а тогда пропала бы и защита, ради которой SE-0391 существует.

Размен назван честно: реестр без подписей запрещает потребителям строгую настройку. Для внутреннего реестра это приемлемо, для публичного — нет. Порядок работ, если делать всерьёз: подписывать архивы в пайплайне публикации, положить корневой сертификат в `trustedRootCertificatesPath`, снять послабление.

## Влезает ли в бесплатный тариф

Да, с двузначным запасом. Один резолв версии — четыре запроса (список, метаданные, манифест, архив); полный резолв двадцати пакетов ≈ 80. И происходит он редко: `Package.resolved` закоммичен, значит резолв случается на CI и на чистых клонах, а не при каждой сборке.

| Ресурс | Бесплатно | Нужно реестру |
|---|---|---|
| Workers | 100 000 запросов/день | сотня полных резолвов ≈ 8 000 |
| D1 | 5 ГБ, 5 млн строк чтения/день | одна строка на запрос |
| R2 | 10 ГБ-месяц, 10 млн чтений/месяц | 20 пакетов × 20 версий × 200 КБ ≈ 80 МБ |

Отдельно важное именно для реестра: **у R2 нулевая плата за исходящий трафик**. Реестр по природе раздаёт больше, чем принимает, и на S3 egress был бы основной статьёй расходов.

Единственное место, упиравшееся в лимит 10 мс CPU, — публикация; после переноса проверки суммы в R2 его нет.

## Известные ограничения

Код написан без доступа к `wrangler` и Swift-тулчейну: логика и контракт эндпоинтов проверены тестами, но ни `wrangler dev`, ни `swift package resolve` против живого реестра ни разу не запускались. Прежде чем считать реализацию рабочей, стоит прогнать [swift-package-registry-compatibility-test-suite](https://github.com/swiftlang/swift-package-registry-compatibility-test-suite) — официальный набор проверок совместимости с SE-0292.

Самое вероятное место расхождения — заголовки `Link` и точная форма JSON метаданных: спецификация допускает необязательные поля, а клиент к части из них относится строже, чем текст обещает.
