# kufar-ios — воркспейс

Демо архитектуры к документу [architecture-ios-app.md](https://github.com/yklishevich/kufar-ios-demo/blob/main/architecture-ios-app.md): **6 команд, 6 репозиториев, 20 SPM-пакетов, 43 таргета, свой пакетный реестр**.

## Быстрый старт

```bash
git clone https://github.com/yklishevich/kufar-ios-demo.git && cd kufar-ios-demo
./Tools/bootstrap.sh    # клонирует 6 репозиториев команд и открывает воркспейс
```

Дальше в Xcode: схема `KufarDemo`, симулятор, ⌘R. Тесты — ⌘U.

Если хочется просто читать код: единственный `switch` по вертикалям на всё приложение — [`SearchScreen.swift`](https://github.com/yklishevich/kufar-search/blob/main/kufar.Search/Sources/SearchUI/SearchScreen.swift), композиционный корень целиком — [`AppComposition.swift`](https://github.com/yklishevich/kufar-platform/blob/main/kufar.AppComposition/Sources/AppComposition/AppComposition.swift), остальное — в таблице «Где что смотреть» ниже.

## Как это устроено

**Адрес — не идентичность.** Пакеты подключаются через [пакетный реестр](https://github.com/yklishevich/kufar-ios-demo/blob/main/registry/README.md) (SE-0292): в манифесте стоит имя, а не URL.

```swift
.package(id: "kufar.GoodsContracts", from: "1.0.0")
```

Разница не косметическая. С гит-зависимостями identity **и есть** адрес, и отсюда цепочка: URL указывает на репозиторий → `Package.swift` ищется в корне → версия это тег → тег принадлежит репозиторию целиком → **один пакет на репозиторий**. Двадцать один пакет автоматически означал двадцать один репозиторий: структуру диктовал инструмент.

С реестром упаковка стала решением. **Репозиторий — на команду**, внутри пакеты:

```
kufar-ios/                            ← воркспейс, не репозиторий
├── KufarWorkspace.xcworkspace        ← открывать нужно именно его
├── Tools/{bootstrap, publish, deplint, check-registry, reset-all}
├── registry/                         ← реализация реестра на Cloudflare
│
├── goods_team/                       ← репозиторий kufar-goods
│   ├── kufar.GoodsContracts/         ← маршруты, data-only
│   └── kufar.Goods/                  ← домен, данные, экраны
│
└── platform_team/                    ← репозиторий kufar-platform
    ├── kufar.Foundation/
    ├── kufar.Navigation/
    ├── …
    └── KufarDemoApp/                 ← Xcode-проект приложения, не пакет
```

Шесть репозиториев по числу команд. Границы владения совпали с границами репозиториев: `CODEOWNERS` стал одним файлом на репозиторий вместо двадцати одного, а правка контракта вместе с реализацией — одним коммитом вместо двух PR. Версии при этом независимы, теги несут имя пакета: `kufar.Foundation-1.2.0`.

**А собирается всё локально** — через воркспейс. Xcode подменяет зависимость папкой, поэтому правка в `kufar.Foundation` видна в `kufar.Goods` сразу, без публикации версии.

> ### ⚠️ Одно жёсткое правило
>
> Подмена сопоставляет зависимость с папкой по **identity**, и для реестра она равна `scope.Name`. Значит:
>
> **имя папки пакета == идентичность в реестре**, то есть `kufar.Foundation`
>
> Имя репозитория при этом не значит ничего. Отступишь от формата — Xcode откажется подменять, и правка в соседнем пакете перестанет быть видна до публикации:
>
> ```
> unable to override package 'Foundation' because its identity
> 'kufar.foundation' doesn't match override's identity
> (directory name) 'foundation'
> ```
>
> Правила этого нет в документации — оно найдено экспериментом, см. [registry/README.md](https://github.com/yklishevich/kufar-ios-demo/blob/main/registry/README.md). Линтер его проверяет.

Ещё два инструмента, оба разовые: `Tools/check-registry.sh` проверяет, что реестр отвечает и отдаёт ожидаемые версии, `Tools/reset-all.sh` схлопывает историю всех репозиториев к одному коммиту.

**Режимы `bootstrap.sh`:**

```bash
./Tools/bootstrap.sh            # клонирует недостающее и открывает воркспейс
./Tools/bootstrap.sh --status   # что уже есть, что отсутствует
./Tools/bootstrap.sh --pull     # обновить всё разом
```

Воркспейс — тоже репозиторий, но особенный: в нём README, документ, `Tools/`, реестр и сам `.xcworkspace` — и ни строчки кода приложения. Папки команд заигнорены целиком (`*_team/`), их поднимает `bootstrap.sh`. Это мета-репозиторий: точка входа, а не код.

**Публикация под своим владельцем.** Резолв зависимостей от владельца не зависит — их адресует реестр, а гит хранит только исходники. Поэтому достаточно создать репозитории и запушить:

```bash
./Tools/publish.sh --check                  # gh установлен? залогинен?
./Tools/publish.sh --dry-run <твой-логин>   # что будет создано
./Tools/publish.sh <твой-логин>             # создать и запушить
```

Плюс свой реестр — [`registry/`](https://github.com/yklishevich/kufar-ios-demo/blob/main/registry/README.md), там инструкция по развёртыванию.

**Повседневная синхронизация.** Локально Xcode собирает рабочую копию, CI — то, что в гите. Расхождение между ними и есть самая частая причина «у меня собирается, на билд-сервере нет»: правки лежат незакоммиченными в восьми репозиториях сразу. Один проход закрывает:

```bash
./Tools/publish.sh --push --dry-run   # что будет закоммичено и с каким сообщением
./Tools/publish.sh --push             # закоммитить и запушить всё изменённое
./Tools/publish.sh --push -m "текст"  # своё сообщение вместо автоматического
```

Сообщение выводится из того, что реально изменилось: `kufar-search: kufar.Search, kufar.SearchContracts`.

Версию поднимает флаг `--tag`, и по умолчанию он ставит **patch**:

```bash
./Tools/publish.sh --push --tag         # 1.0.0 → 1.0.1
./Tools/publish.sh --push --tag minor   # 1.0.0 → 1.1.0
./Tools/publish.sh --push --tag major   # 1.0.0 → 2.0.0
```

Тег получает только то, у чего есть `Package.swift`: на пакет ссылаются чужие манифесты, и резолверу нужно знать, что скачивать. Воркспейс и `KufarDemoApp` пакетами не являются — версия там была бы украшением. Тег ставится без `-f`: переписать уже выпущенную версию значит подсунуть другой код тому, кто её зарезолвил и закешировал.

Выбор уровня остаётся на авторе, и скрипт его не проверяет — этого не умеет никто, кроме компилятора чужого потребителя. `patch` — реализация поправлена, публичный API не тронут. `minor` — API расширен, старый код цел. `major` — сигнатура изменена, символ удалён, в закрытый enum добавлен кейс. Поставить `patch` на ломающее изменение значит соврать в теге: резолвер молча подтянет его всем, кто написал `from:`, и уронит их сборку.

## Главное: вертикали — не вкладки

Лента на классифайде одна. Вертикаль выбирается **категорией**, а не переключением таба: пользователь ищет «пылесос» и «Golf» в одном и том же поле, а подаёт объявление в одну и ту же форму. Таб-бар отражает режимы работы — Поиск, Подать, Избранное, Профиль.

```
┌─────────────────────────────────────┐
│  Поиск                    [фильтры] │   ← searchable + toolbar
├─────────────────────────────────────┤
│  Все категории · 21 объявление      │
│  ┌───┐ Пылесос Bosch      190 р.    │   goods
│  ┌───┐ Volkswagen Golf  34 500 р.   │   auto
│  ┌───┐ Кресло             120 р.    │   goods
└─────────────────────────────────────┘
        ↓ тап
   switch ref.vertical → GoodsRoute.details / AutoRoute.details
```

Отсюда два следствия, ради которых всё и затевалось:

**Добавление вертикали не трогает таб-бар.** Оно трогает ровно два места: дерево категорий на бэкенде и один `switch` в поиске, куда компилятор приведёт сам.

**Появляются модули, которые знают про все вертикали сразу.** Их два, и оба не принадлежат вертикалям: поиск и подача. Объединяет их то, что **вертикаль определяется внутри флоу, а не до него**: на входе в поиск запрос ещё пустой, на входе в подачу категория ещё не выбрана. Владельца среди вертикалей у такого флоу нет. Экран выбора категории показывает категории всех вертикалей сразу, поэтому положить его можно только внутрь одной из них — и тогда она станет шлюзом для остальных: команде авто придётся открывать PR в репозиторий товаров, чтобы добавить свой шаг подачи. Отсюда собственный владелец у поиска и у подачи. Знают они только *контракты* — `GoodsInterface`, `AutoInterface`; ни одного импорта чужой реализации, и SwiftPM за этим следит.

Оба построены на одних и тех же двух механизмах: дерево категорий (`CatalogContracts`) и рендерер схем (`SchemaKit`). В поиске схема рисует фильтры, в подаче — форму, в карточке — блок атрибутов. Одна схема на бэкенде описывает и «по чему ищем», и «что спрашиваем», и «что показываем».

```
       категория (дерево с бэкенда)
              │
      ┌───────┴───────┐
   поиск            подача
  (читает)          (пишет)
      │                │
      └──── switch vertical ────→ GoodsRoute / AutoRoute
```

## Кто чем владеет

| Команда | Репозитории | Что отдаёт наружу |
|---|---|---|
| **Platform Core** | `kufar.Foundation`, `kufar.Navigation`, `kufar.Analytics` | `SharedKernel`, `NetworkingInterface`, `Networking`, `NetworkingTesting`, `Navigation`, `AnalyticsAPI`, `AnalyticsImpl` |
| ↳ та же | `kufar.DesignTokens`, `kufar.DesignComponents` | `DesignTokens`, `DesignComponents` |
| ↳ та же | `kufar.SchemaKit`, `kufar.ListingKit` | `SchemaKit`, `ListingKit` |
| ↳ та же | `kufar.AppFeature`, `kufar.AppComposition`, `KufarDemoApp` | `AppFeature`, `AppComposition`, приложение |
| **Поиск** | `kufar.CatalogContracts`, `kufar.SearchContracts`, `kufar.Search` | `CatalogContracts`, `SearchInterface`, `Search` |
| **Подача** | `kufar.PostingContracts`, `kufar.Posting` | `PostingInterface`, `Posting` |
| **Товары** | `kufar.GoodsContracts`, `kufar.Goods` | `GoodsInterface`, `Goods` |
| **Авто** | `kufar.AutoContracts`, `kufar.Auto` | `AutoInterface`, `Auto` |
| **Identity** | `kufar.SessionContracts`, `kufar.IdentityContracts`, `kufar.Identity` | `SessionInterface`, `SessionInterfaceTesting`, `ProfileInterface`, `AuthInterface`, `Profile`, `Auth` |

В каждом репозитории лежит `.github/CODEOWNERS` — так владение выражают в жизни, а не в договорённостях: GitHub по этому файлу автоматически назначает ревьюеров и, при включённой защите ветки, не даёт смержить PR без апрува владельца.

Общее правило одно: **на контрактных пакетах вторым владельцем стоит платформенная команда.** Контракты — публичное API репозитория, ломающее изменение в них останавливает чужие команды, и это единственное место, где такое возможно.

Синтаксис — `<шаблон пути> <владелец> [<владелец> ...]`. Репозиторий держит несколько пакетов, поэтому файл один, а разделение внутри задаётся путями:

```
*                         @kufar/ios-search
/kufar.SearchContracts/   @kufar/ios-search @kufar/ios-platform
/kufar.CatalogContracts/  @kufar/ios-search @kufar/ios-platform
```

Строка с двумя владельцами означает «файлы принадлежат обеим командам»: обе получают запрос на ревью, но апрува достаточно **от любой**. AND в `CODEOWNERS` не выражается вообще — если нужен апрув именно от платформы, это отдельная CI-проверка. И побеждает **последнее** совпавшее правило, а не сумма: при нескольких строках владельца приходится перечислять заново в каждой.

Место файла — не деталь оформления. GitHub читает `CODEOWNERS` только из корня репозитория, из `.github/` или из `docs/`. Вложенный `kufar.Foundation/CODEOWNERS` игнорируется молча — ни ошибки, ни предупреждения, — и обнаруживается это тем, что в чужой PR никого не позвали. Пока проект был устроен как «репозиторий = пакет», такие файлы лежали в корнях и работали; после перехода на «репозиторий = команда» их пришлось собрать в один на репозиторий. Место проверяет `deplint.py`, правило 11.

Отсюда же следует, что **пакетная граница владение не разделяет**: `CODEOWNERS` работает по путям, и отдельный ревью-гейт на директорию можно завести, ничего не выделяя в пакет. Пакет даёт другое — возможность переселить код в другой репозиторий, не тронув ни одного манифеста потребителя.

### Почему у приложения свои репозитории, но не своя команда

`kufar.AppComposition` — единственный, кто зависит от всех: композиционный корень, разбор диплинков, состав флейворов. Отдельный репозиторий ему нужен именно поэтому — у него самый широкий граф, и правка в любой вертикали пересобирает его последним. Рядом `KufarDemoApp` — сам Xcode-проект, единственный репозиторий воркспейса, который вообще не пакет.

А вот отдельная команда — нет. И библиотеки, и app shell, и CI, и релизный поезд — работа одного типа: она обслуживает чужую разработку, а не выпускает продуктовые фичи. При десятке iOS-разработчиков это те же люди, что делают платформу.

Чего делать точно нельзя — отдавать эти репозитории продуктовой команде. Кто владеет композиционным корнем, тот решает, что попадает в сборку, и продуктовая команда в этой роли начнёт гейтить релизы всех остальных.

Внутри репозитория проходит ещё одна граница, и она важнее, чем кажется: `kufar.AppFeature` (корневой флоу) зависит **только от контрактных пакетов**, поэтому собирается и тестируется без сети, без единого `*Data` и без единой вертикали. `kufar.AppComposition` — чистая проводка, единственное место с конкретными реализациями.

Разделены они именно на **пакеты**, а не на таргеты внутри одного, и разница тоньше, чем кажется.

Оставь два таргета в одном пакете — запрет никуда не денется: SwiftPM проверяет зависимости на уровне таргета, и `import Goods` в `AppFeature` не соберётся, пока `Goods` не появится в его `dependencies:`. Компилятор всё так же на страже.

Потеряется другое. Список зависимостей **пакета** перестанет быть утверждением: в нём будут лежать все вертикали, потому что они нужны проводке. Сегодня, чтобы протащить вертикаль в корневой флоу, надо добавить пакет — это видно в диффе манифеста и ловится на ревью. В общем пакете хватит дописать имя в `dependencies:` таргета, ничего нового не подключая.

Дальше — механика: любой потребитель `AppFeature` резолвил бы весь граф вместе с вертикалями; версия стала бы общей, и корневой флоу не выпустить, не выпустив проводку. Поэтому граница проведена по пакету — это не педантизм, а разница между «нельзя» и «не принято».

Риск у этой роли известный: каждая новая вертикаль требует строчки в `AppComposition`, то есть PR в чужой репозиторий. Лечится тем, что строчка должна оставаться тривиальной — один `.concat` и один кейс таба. Как только в корне заводится вертикально-специфичная логика, платформенная команда становится бутылочным горлышком по-настоящему.

### Почему команд шесть, а пакетов двадцать один

Соблазн сделать по команде на пакет велик и неверен: границы пакетов определяются релизными циклами, границы команд — людьми, и совпадают они не всегда.

У платформенной команды пакетов девять — токены генерируются из Figma, каркас карточки меняется реже вертикалей, приложение собирается последним. Разные релизные циклы, одни люди.

Раньше здесь была вынужденная связка «пакет = репозиторий»: `.package(url:)` указывает на репозиторий, а `Package.swift` ищется в его корне, значит из одного репозитория больше одного пакета не отдать. С переходом на реестр это ограничение снято — упаковка в репозитории стала **решением**, а не следствием инструмента, и сколько пакетов лежит в одном репозитории, на граф зависимостей больше не влияет.

Обратный случай — тоже реальный: **одна кодовая база на две команды** здесь не встречается, и это хорошо. Как только два владельца делят один репозиторий, `CODEOWNERS` превращается в лабиринт, а конфликты релизов приходится разруливать вручную.

Получившееся деление ложится на словарь Team Topologies: `goods`, `auto`, `search`, `posting` и `identity` — **stream-aligned**, у каждой свой кусок пользовательского пути и свои метрики; `platform_team` — **platform team**, она обслуживает чужую разработку и ничего не выпускает сама.

Подача выделена в отдельную команду не по размеру кода, а по метрике: она отвечает за completion rate воронки и время до публикации, то есть напрямую двигает ликвидность — главный показатель классифайда. Отдай её поиску — и у одного владельца окажутся две разные метрики, конкурирующие за его внимание.

Честная оговорка, которую стоит проговорить самому: шесть — это **границы владения**, а не штатное расписание. В компании масштаба Kufar `search_team` вполне может совпадать с платформенной, а identity — быть её половиной. Ценность схемы от этого не падает: модули режут под то, как команды разойдутся **потом**, потому что разъезжаться по живому дороже, чем заложить швы заранее. Но заявлять шесть команд там, где их две, — напрашиваться на неудобный вопрос.

## Почему пакетов так много

Двадцать пакетов на две вертикали выглядит избыточно ровно до вопроса «а что резолвится, когда я подключаю одну строчку». Пакет — единица не только кода, но и **разрешения зависимостей**: подключив продукт, ты резолвишь весь пакет целиком со всеми его зависимостями. Отсюда правило — то, что подключают многие, живёт в пакете с минимальным графом.

**`kufar.GoodsContracts` отдельно от `kufar.Goods`.** Поиск берёт `GoodsInterface` — один enum на десять строк. Будь он продуктом `kufar.Goods`, поиск резолвил бы вместе с ним дизайн-систему, ListingKit, аналитику и навигацию — всё, от чего зависит реализация вертикали.

Само по себе это не смертельно: сборку поиска лишние ограничения не ломают, пока в его графе нет второй вертикали с несовместимым диапазоном. Ломается другое — **контракт и реализация делят один номер версии**, а меняются с разной частотой: маршруты раз в квартал, экраны ежедневно.

Сценарий, где это стреляет:

1. «Товары» добавляют `GoodsRoute.reviews` — и в том же релизе `kufar.Goods 4.0` переезжают на `DesignComponents 3.0`;
2. поиску нужен новый маршрут, значит нужен `kufar.Goods 4.0` — взять один enum, не взяв всю реализацию, нельзя;
3. поиск начинает транзитивно требовать `DesignComponents >= 3.0`;
4. приложение тянет ещё и `kufar.Auto`, который пока на `2.x`, — диапазоны не пересекаются, резолв падает.

Поиск заблокирован, хотя не написал ни строчки про дизайн-систему. С разделёнными контрактами шаг 1 распадается надвое: `kufar.GoodsContracts 2.0` уносит новый маршрут и **ни одного нового ограничения**, а `kufar.Goods 4.0` со своей дизайн-системой едет отдельно и никого не держит.

**И главное — цикла бы не получилось развязать.** `kufar.Auto` зависит от `kufar.SearchContracts`: экран дилера открывает поисковый запрос «все объявления продавца». `kufar.Search` зависит от `kufar.AutoContracts`: тап по результату открывает карточку авто. Если бы контракты жили внутри своих feature-пакетов, вышло бы `kufar.Search → kufar.Auto → kufar.Search`, и SwiftPM отказался бы резолвить граф. Вынос контрактов — не оптимизация, а условие существования схемы.

Здесь напрашивается возражение: пусть контракты остаются внутри, но отдаются отдельным **продуктом** — разве этого не достаточно? Нет, и причина механическая. Чтобы сослаться на любой продукт чужого пакета, надо сначала объявить сам пакет:

```swift
dependencies: [.package(id: "kufar.Search", from: "1.0.0")],
targets: [.target(name: "AutoUI", dependencies: [
    .product(name: "SearchContracts", package: "kufar.Search")   // ← требует строки выше
])]
```

Значит `kufar.Auto` объявит `kufar.Search`, а `kufar.Search` объявит `kufar.Auto`, и резолв упадёт:

```
cyclic dependency declaration found: kufar.Search -> kufar.Auto -> kufar.Search
```

Проверка идёт по графу **пакетов** и происходит до построения графа таргетов. Граф таргетов при этом был бы ацикличным — `AutoUI → SearchContracts`, `SearchUI → AutoContracts`, а контрактные таргеты не зависят ни от чего, — но до него дело не доходит.

Отсюда точная формулировка: ограничение — следствие выбора «много пакетов», а не свойство языка. Единица зависимости здесь пакет, поэтому и контракт обязан быть пакетом. Были бы `Search` и `Auto` таргетами одного пакета, взаимные ссылки на контрактные таргеты резолвились бы нормально. Контракты и там пришлось бы отделить — цикл между таргетами запрещён ровно так же, — но ценой ошибки был бы отказ сборки одного пакета, а не нерезолвимый граф на весь проект.

**`kufar.Foundation` отдельно от всего SwiftUI** — у него платформенная планка iOS 15 против iOS 17 у остальных: этот код переиспользуют расширения, виджет и часы. Платформы объявляются на пакет, не на таргет.

**`kufar.DesignTokens` отдельно от компонентов** — токены генерируются из Figma и релизятся своим циклом.

**`kufar.CatalogContracts` отдельно от `kufar.SearchContracts`.** Пока дерево категорий нужно было только фильтрам, оно жило в контракте поиска. Появилась подача — и у понятия стало два потребителя из разных команд, то есть оно перестало принадлежать поиску. Это и есть момент, когда контракт выносят: не раньше, иначе оверинжиниринг, и не позже, иначе один владелец начинает диктовать другому.

**`kufar.SchemaKit` отдельно от `kufar.ListingKit`** — рендерер схем нужен двоим: экрану фильтров в поиске и блоку атрибутов в карточке. Сам `ListingKit` про него не знает: блок атрибутов приезжает в слот от вертикали. Два пакета одного репозитория не обязаны зависеть друг от друга.

## Границу держит SwiftPM, а не договорённость

Вертикаль объявляет ровно один продукт — assembly:

```swift
products: [
    .library(name: "Goods", targets: ["Goods"])
],
targets: [
    .target(name: "GoodsDomain", ...),   // внутренний
    .target(name: "GoodsData",   ...),   // внутренний
    .target(name: "GoodsUI",     ...),   // внутренний
    .target(name: "Goods",       ...)    // ← продукт
]
```

`import GoodsUI` из чужого пакета не соберётся: продукта с таким именем не существует. Раньше это ловил линтер — теперь линтер лишь дублирует то, что и так невозможно.

Второй слой — уровни доступа. Внутри пакета таргеты тоже отдельные модули, поэтому `public` там значит не «наружу», а «в соседний таргет», и помечать им всё подряд — значит писать в исходнике обратное намерению. Расставлено по факту: `public` — только то, что стоит в сигнатурах ассамблеи (протокол репозитория и его модель); `package` (Swift 5.9) — то, что пересекает границу таргета внутри пакета (`*Destinations`, реализации репозиториев); без модификатора — экраны, которые видит только собственный `*Destinations`. Ни один экран вертикали не `public`.

Композиционный корень при этом не знает ни одного экрана: `GoodsAssembly.makeDestinations(...)` возвращает `some ViewModifier`. Непрозрачный тип прячет конкретику от программиста, но не от компилятора — в отличие от `AnyView`.

## Запуск

**Открывать нужно `KufarWorkspace.xcworkspace`, а не отдельный `Package.swift`.**

Это не вкусовщина, а выбор режима. Внутри воркспейса Xcode подменяет URL-зависимости локальными папками — ты собираешь HEAD всех репозиториев, и правка в `kufar.Foundation` видна в `kufar.Goods` сразу, без тега. Откроешь одиночный пакет — SwiftPM пойдёт в сеть и соберёт по **тегам**: это тоже работает, но ты получишь последние выпущенные версии соседей, а не их рабочие копии рядом.

```bash
open KufarWorkspace.xcworkspace     # или ./Tools/bootstrap.sh
```

Дальше выбрать схему `KufarDemo`, симулятор, ⌘R. Тесты — ⌘U.

```bash
xcrun simctl openurl booted "kufar://search?q=Golf&cat=auto.cars"  # поиск с категорией

xcrun simctl openurl booted "kufar://goods/g-1"                    # прямой маршрут

```

**Линтер:** `python3 Tools/deplint.py` — работает без Xcode и без сети, читает манифесты.

## Проверки

`.github/workflows/` — две сборки, отражающие два режима резолва. `workspace.yml` собирает воркспейс на HEAD всех репозиториев (локальная подмена, версии не участвуют) и гоняет `deplint` отдельной job на ubuntu — без Xcode и сети. `versioned.yml` собирает приложение **без** соседних папок, резолвя зависимости из гита по тегам, в двух прогонах: `pinned` (как есть в лок-файле) и `latest` (лок-файл удалён). Первый режим ловит рассогласование незарелиженной работы, второй — забытый тег, пустое пересечение диапазонов и не поднятый пол в манифесте. Подробнее — в разделе «Две сборки, потому что режима два».

`python3 Tools/deplint.py` — десять правил поверх того, что уже гарантирует SwiftPM: разрешимость импорта через продукты, объявленность в манифесте, направление зависимостей, запрет горизонтали между вертикалями, правило одного корня, отсутствие SwiftUI в контрактах, «дешевизна» контрактных пакетов, `import *Testing` только под `#if DEBUG`, отсутствие циклов между пакетами, мёртвые зависимости.

`platform_team/kufar.AppComposition/Tests/ArchitectureTests` — те же границы, но запускаются в Xcode вместе с обычными тестами. Отдельно проверяют, что внутренние таргеты вертикалей не просочились в products.

`platform_team/kufar.AppFeature/Tests/AppFeatureTests` — собираются **без** сети, без единого `*Data` и без единой вертикали: пакет `kufar.AppFeature` зависит только от контрактных пакетов. Логаут очищает все стеки, push не уезжает в соседний таб, `replaceLast` не растит глубину, диплинк разбирается во всех вариантах, все маршруты переживают `NavigationPath.codable`.

## Что осталось за кадром

**Пакетный реестр — не «за кадром», а в [`registry/`](https://github.com/yklishevich/kufar-ios-demo/blob/main/registry/README.md).** Реализация SE-0292 на Cloudflare Workers: R2 под архивы, D1 под метаданные, пять GET-эндпоинтов, публикация из `Tools/publish.sh --push --tag`, тесты в `workerd`. Развёрнут на `spm-registry.byklishevich.com`, все двадцать один пакет резолвятся через него.

**Правило про имя папки найдено экспериментом, а не в документации.** Сначала выяснилось, что `swift package edit` вообще отказывается работать с registry-зависимостью:

```
error: registry dependency 'kufar.Toolbox' can't be edited
```

Из чего следовал вывод, что локальная подмена с реестром несовместима и мигрировать нельзя. Неверный: в Xcode ошибка оказалась другой и куда полезнее —

```
unable to override package 'Toolbox' because its identity 'kufar.toolbox'
doesn't match override's identity (directory name) 'toolbox'
```

Механизм подмены есть, не совпадала только идентичность: у зависимости она со скоупом, у локальной копии берётся из имени директории. Переименовали папки в `kufar.Name` — заработало. CLI и Xcode здесь ведут себя по-разному, и остановись проверка на первом результате, вывод был бы противоположным.

**Что это дало.** Упаковка в репозитории перестала быть следствием инструмента: адрес больше не идентичность, значит несколько пакетов могут лежать в одном репозитории с независимыми версиями, а переезд пакета между репозиториями невидим для потребителей.

### Почему правила 1–2 линтера не дублируют компилятор

Естественный вопрос к `deplint.py`: зачем проверять, что импорт объявлен в манифесте, если несобирающийся импорт и так упадёт на сборке. Ответ — потому что он не всегда падает.

SwiftPM кладёт в пути поиска и прямые зависимости, и транзитивные, и объявленные продукты. Из этого следуют два разных провала:

**Внутри пакета** таргет может импортировать соседний таргет, не объявив его в `dependencies`, — компилятор промолчит. На это есть штатный флаг, опциональный и по умолчанию выключенный:

```
swift build --explicit-target-dependency-import-check error   # либо warn, либо none
```

**Между пакетами** транзитивно достижимый модуль импортируется без объявления — и **этого не ловит даже флаг**. Проверено автором разбора SwiftPM на минимальном примере: таргет импортирует модуль, доступный через посредника, флаг включён, ошибки нет.

Второй случай для этого проекта и есть настоящий. `kufar.ListingKit` объявляет `DesignTokens`, `DesignComponents` и `SharedKernel`, и никакого `*Interface` в его замыкании сегодня нет. Но замыкание ему не принадлежит: достаточно, чтобы `kufar.DesignComponents` завтра взял чей-нибудь контракт, — и `GoodsInterface` станет достижим из `ListingKit`, а его собственный манифест не изменится ни на строчку.

**Явная сборка модулей** (`Explicitly Built Modules`, умолчание для Swift начиная с Xcode 26) на это не влияет: она про то, **как** модули собираются — сканирование графа, отдельная задача сборки на модуль, явный список готовых модулей на входе компиляции, — а не про то, что разрешено импортировать. Выигрыш там детерминизм и кеширование, не контроль доступа.

**Флаг в CI не включён намеренно.** Все сборки здесь идут через `xcodebuild`, а флаг — от `swift build`; ради него понадобилась бы отдельная macOS-job с десятикратным тарифом и настройкой реестра для каждого пакета. Ловит он ровно ту половину, которую `deplint.py` уже ловит на ubuntu за секунды, а вторую половину — ту, ради которой всё затевалось, — не ловит вовсе.

| | Репозиториев | Атомарное изменение | Реорганизация команд |
|---|---|---|---|
| Было | 21 | между любыми пакетами дорого | бесплатна: правка `CODEOWNERS` |
| **Стало: репозиторий на команду** | 6 | внутри команды бесплатно | переезд пакета `subtree` |
| Монорепозиторий | 1 | везде бесплатно | бесплатна |

Выбран средний вариант. Он покупает внутрикомандную атомарность — правка контракта вместе с реализацией стала одним коммитом вместо двух согласованных PR — ценой переезда пакетов при реорганизации команд: `git subtree` сохраняет коммиты, но меняет SHA, а обсуждения в PR остаются в старом репозитории. Размен приемлем, потому что команды перекраивают реже, чем правят код через границу пакета.

Монорепозиторий выигрывает по обеим колонкам и всё равно отклонён: он снимает не только трение, но и **изоляцию**, ради которой всё построено. Граница, которую ничто не охраняет, держится на дисциплине ревьюеров; здесь её охраняет отдельный репозиторий с собственными правами доступа и `deplint.py` в CI.

Переезд делался через `git subtree`, с переносом коммитов, а не копированием файлов. Той истории, однако, уже нет: `Tools/reset-all.sh` схлопнул все репозитории к одному коммиту, потому что для проекта, который открывают посмотреть на архитектуру, черновая история — шум. Что именно потерялось, скрипт перечисляет в своей шапке.

**Чего реестр не решает.** Добавление вертикали остаётся дорогим при любом дроблении, кроме полного монорепозитория: `SharedKernel` и его потребители в разных репозиториях, значит фазовый переход из 2.3 никуда не девается. И **историю он не сохраняет** — она свойство репозитория, а не имени пакета.

**Цена входа, которую теперь платим.** Публикация стала своей работой: собрать архив, посчитать сумму, загрузить, зарегистрировать — всё это делает `publish.sh --tag`, но делает потому, что кто-то это написал. Публичного хостинга для Swift-реестров нет, сервер свой. У реестровых зависимостей нет веток: `.package(url:branch:)` для отладки чужого пакета не сделаешь, только версии.

И архивы не подписаны — SE-0391 не реализован. Это не косметика: значение `signing.onUnsigned` по умолчанию `prompt`, а резолв в Xcode неинтерактивен, и вопрос там превращается в отказ сборки. Поэтому политика задана явно в `registries.json` и закоммичена — через `registryOverrides` для своего хоста, чтобы не снимать проверку подписи со всех реестров сразу. Проверить резолв без участия Xcode: `./Tools/check-registry.sh`.

**Сети.** `APIClient` вызывается, но возвращает пустые данные — репозитории отдают фикстуры.

**Persistence**, downsampling изображений, `_printChanges` — описаны в документе, но чтобы увидеть эффект, нужна настоящая лента с фотографиями.
